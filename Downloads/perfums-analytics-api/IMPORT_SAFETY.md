# Безпечна політика імпорту

## Пріоритет джерел

1. Офіційний повний місячний файл фіналізує місяць і замінює його відповідний набір даних.
2. Щотижневий файл виконує UPSERT тільки за ключами, які реально присутні у файлі.
3. Порожній `shift_plan_ml` у новому ML не стирає вже відомий план зміни.
4. Нові регіони, відділи та продавці створюються в тій самій транзакції, що й імпорт.
5. Повторний файл із тим самим SHA-256 не імпортується двічі.

## Ключі оновлення

- продаж відділу: `sale_date + department_id`;
- зміна продавця: `shift_date + employee_id + department_id`;
- зарплата: `payroll_date + employee_id + department_id`;
- план: `snapshot_date + plan_month + plan_type + object`;
- місячне виконання: `performance_month + employee_id + department_id`.

## Відповіді API

- якщо є фінальний рядок `employee_monthly_performance`, API повертає офіційний місячний результат;
- якщо фінального звіту немає, API агрегує `employee_shifts` і позначає результат як проміжний;
- якщо план відсутній хоча б для однієї зміни, `completion_percent` повертається як `null`, а `plan_missing_shifts` показує кількість пропусків.

## Порядок місячного завантаження

1. Файл зарплати/денних змін за повний місяць.
2. `PlanMin` за повний місяць.
3. `PlanBNAC` за повний місяць.
4. Офіційний файл виконання плану співробітниками.
5. Перевірка `/api/meta` та контрольних працівників/відділів.
